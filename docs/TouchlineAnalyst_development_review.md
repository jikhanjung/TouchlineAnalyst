# PitchWatch / PitchStitch 개발 논의 정리

## 1. 논의의 출발점

Veo·Pixellot과 같은 자동 촬영·분석 시스템을 검토하면서, 다음과 같은 현실적인 제약이 확인되었다.

- 듀얼 광각 카메라로 경기장 전체를 촬영하면 원경 선수의 픽셀 크기가 매우 작아진다.
- 4K 영상에서도 근경 선수는 비교적 잘 검출되지만, 원경 선수는 타일로 잘라 분석해야 성능이 올라간다.
- 원경에서는 등번호 OCR이 특히 어렵다.
- 8K 촬영은 분석에 유리하지만 저장공간, 디코딩 속도, 발열, 처리시간 부담이 크다.
- 파노라마 영상을 먼저 생성하면 처리 구조는 단순해지지만, 대용량 중간 파일과 리샘플링 손실이 생긴다.
- 카메라별 원본을 직접 분석하면 화질과 처리 효율은 좋아지지만 멀티카메라 통합과 동기화가 복잡해진다.
- 선수 검출이 가능하더라도, 같은 선수를 90분 동안 동일 ID로 유지하는 것은 별개의 어려운 문제다.

따라서 PitchWatch의 핵심은 처음부터 “완전 자동 전술 분석”을 구현하는 것이 아니라, **후속 기능이 의존할 수 있는 신뢰성 높은 관측 데이터 스트림을 만드는 것**으로 정리할 수 있다.

---

## 2. 전체 워크플로

멀티카메라 시스템을 전제로 하면 핵심 기반 단계는 다음 세 가지다.

```text
0. 시간 동기화
   - 오디오 기반 초기 정렬
   - 호각·충격음 anchor 검출
   - 장시간 clock drift 보정

1. 공간 calibration
   - 카메라 intrinsic / 렌즈 왜곡 보정
   - 경기장 landmark 지정
   - 영상 좌표 → 경기장 좌표 변환

2. perception
   - 선수·심판·공 검출
   - 단기 tracking
   - 전체 프레임과 타일 검출 통합
   - 카메라 간 관측 통합

3. 후속 응용
   - radar
   - virtual PTZ
   - stitching / follow-cam
   - 전술 분석
   - 이벤트 분석
   - 선수 식별
   - 통계 및 리포트
```

소프트웨어 개발의 우선순위는 **0 → 1 → 2** 순으로 잡는 것이 적절하다.  
특히 나머지 모든 기능의 품질은 2단계 perception 성능에 크게 좌우된다.

## 3. 시간 동기화

### 3.1 왜 중요한가

멀티카메라에서 시간축이 어긋나면 다음 문제가 발생한다.

- 같은 선수가 서로 다른 위치에 있는 것처럼 보인다.
- 카메라 간 track handoff가 실패한다.
- 공의 위치가 카메라별로 크게 달라진다.
- 스티칭 seam에서 객체가 겹치거나 분리된다.
- 이벤트 분석 시점이 흔들린다.

특히 공은 빠르게 움직이므로 몇 프레임의 오차도 큰 위치 오차로 이어질 수 있다.

### 3.2 권장 접근

```text
전체 오디오 cross-correlation
        ↓
대략적인 offset 산출
        ↓
호각·충격음 후보 검출
        ↓
정밀 anchor 매칭
        ↓
clock drift 계산
        ↓
공통 경기 시간축 생성
```

호각은 좋은 sparse anchor지만, 호각만으로 전체 동기화를 해결하면 안 된다.

- 다른 경기장의 호각이 섞일 수 있다.
- 카메라마다 마이크 응답과 노이즈 억제가 다를 수 있다.
- 에코와 반사음이 생길 수 있다.
- 일부 카메라에서 호각이 약하게 녹음될 수 있다.

따라서 전체 오디오 정렬을 기본으로 하고 호각을 정밀 보정과 drift 추정에 사용하는 것이 좋다.

### 3.3 시간 모델

단일 offset보다 다음과 같은 변환이 필요하다.

```text
reference_time = scale × camera_time + offset
```

- `offset`: 녹화 시작 시점 차이
- `scale`: 카메라 clock drift
- 필요하면 구간별 piecewise-linear mapping 사용

프레임 번호보다 파일의 PTS를 기준으로 처리해야 한다.

## 4. 경기장 calibration

### 4.1 calibration의 두 층

#### 카메라 calibration

- 초점거리
- 주점
- 방사 왜곡
- 접선 왜곡
- 촬영 모드별 차이
- 전자식 안정화·수평 보정 영향

동일 카메라와 촬영 설정을 유지한다면 재사용 가능하다.

#### 경기장 calibration

- 영상 landmark와 실제 경기장 좌표의 대응
- homography 계산
- 유효 경기장 영역
- 카메라별 가시 범위
- 경기장 규격

삼각대 위치, 높이, yaw, pitch가 달라질 때 다시 수행한다.

### 4.2 단일 시점의 장점

각 카메라를 독립된 고정 시점으로 취급하면 calibration이 비교적 단순하다.

- 터치라인·골라인 교차점
- 하프웨이라인 교차점
- 페널티지역 모서리
- 골지역 모서리
- 센터서클 교점
- 페널티마크

이런 지점을 직접 찍어 영상 좌표와 경기장 좌표를 대응시킬 수 있다.

최소 4점으로 homography를 계산할 수 있지만, 실제로는 카메라당 8~15개의 landmark를 화면 전체에 분산시키는 것이 좋다.

### 4.3 주의사항

- 선수 위치는 bounding box 중심이 아니라 발의 지면 접점을 사용한다.
- 광각 왜곡 보정 후 homography를 계산한다.
- landmark가 한 직선이나 화면 한쪽에 몰리지 않게 한다.
- 결과 검증을 위해 실제 경기장 선을 영상에 재투영한다.
- 평균 재투영 오차와 위치별 오차를 표시한다.

## 5. 선수·심판·공 검출

## 5.1 범용 YOLO보다 커스텀 모델이 유리한 이유

PitchWatch 영상은 도메인이 매우 제한적이다.

- 카메라 위치와 각도가 반복적이다.
- 경기장 배경이 거의 고정되어 있다.
- 클래스 수가 적다.
- 원근에 따른 선수 크기를 예측할 수 있다.
- 오검출 대상도 반복된다.
- 경기장 밖 사람과 벤치 인원도 일정한 패턴을 가진다.

따라서 실제 PitchWatch 데이터로 YOLO를 파인튜닝하면 다음 항목의 개선을 기대할 수 있다.

- 원경 선수 recall
- 심판·선수 구분
- 벤치 인원과 경기 중 선수 구분
- 경기장 밖 사람의 오검출 감소
- 혼잡 상황에서 선수 분리
- tracklet fragmentation 감소

다만 커스텀 YOLO가 직접 해결하지 못하는 항목도 분명하다.

- 장시간 선수 ID 유지
- 가림 후 동일 선수 복원
- 등번호 OCR
- 패스의 송신자·수신자 판정
- 전술적 의미 해석

### 5.2 클래스 설계

초기 검출 클래스는 단순하게 유지하는 것이 좋다.

```text
player
goalkeeper
referee
ball
```

홈·원정 팀 구분은 검출 이후 별도 분류기로 처리한다.

```text
player crop
    ↓
home / away / goalkeeper / referee
```

등번호는 YOLO 클래스가 아니라 별도의 식별 파이프라인으로 둔다.

## 6. 원근 적응형 타일 분석

### 6.1 타일 분석이 필요한 이유

4K 전체 프레임을 모델 입력 크기로 축소하면 원경 선수는 지나치게 작아진다.  
실제 테스트에서도 원경은 타일로 잘라 넣었을 때 검출 성능이 좋아졌다.

```text
4K/8K 원본
├── 전체 축소본: 전역 상황, 근경 선수
├── 중거리 타일
├── 원경 좌측 타일
├── 원경 중앙 타일
└── 원경 우측 타일
```

### 6.2 권장 방식

- 근경은 전체 축소본 중심
- 중경은 큰 타일
- 원경은 작은 타일을 높은 입력 해상도로 처리
- 타일 경계에 10~20% 중첩
- 결과를 원본 좌표로 복귀
- NMS 또는 유사한 방식으로 중복 제거

카메라가 고정되어 있으므로 일반적인 동적 타일링보다 **경기장 위치에 따른 고정 프로파일**이 더 효율적일 수 있다.

### 6.3 학습 데이터도 타일 구조를 반영

추론만 타일로 수행하고 학습은 전체 프레임으로만 하면 분포 차이가 생길 수 있다.  
훈련 데이터에 다음을 모두 포함하는 것이 좋다.

- 전체 프레임
- 근경 crop
- 중거리 crop
- 원경 타일
- 선수 밀집 구간
- 가림이 심한 구간
- 타일 경계에 걸린 선수

## 7. Tracking의 현실적인 목표

### 7.1 단기 tracklet과 실제 선수 ID는 다르다

#### 로컬 track ID

- 몇 초에서 수십 초 동안 이어지는 임시 ID
- tracker로 비교적 자동화 가능

#### 실제 선수 ID

- `home_player_7`
- `away_player_10`
- 경기 전체에서 유지해야 하는 실제 신원

실제 선수 ID는 검출이나 단기 tracking보다 훨씬 어려운 문제다.

### 7.2 파노라마도 근본 해결책은 아니다

파노라마 영상으로 분석하면 카메라 간 handoff 문제는 줄어들지만 다음 문제는 그대로 남는다.

- 선수 간 교차
- 완전한 가림
- 같은 팀 유니폼의 유사성
- 원경에서의 낮은 해상도
- 가림 후 재등장
- 교체 선수 등장

따라서 파노라마 분석에서도 tracklet association과 identity resolution이 필요하다.

### 7.3 초기 목표

처음부터 90분 동안 22명을 완벽히 식별하는 것을 목표로 하지 않는다.

```text
검출
 ↓
단기 tracking
 ↓
tracklet 생성
 ↓
경기장 좌표 변환
 ↓
익명 또는 팀 단위 분석
```

선수 실명 ID는 이후 단계에서 로스터, OCR, 사용자 보정으로 붙인다.

## 8. OCR과 선수 식별

### 8.1 원경 OCR의 물리적 한계

원경 선수의 전체 높이가 작으면 등번호 영역은 몇 픽셀에 불과하다.

- 압축으로 획이 뭉개진다.
- 셔츠 주름으로 숫자가 변형된다.
- 달릴 때 모션 블러가 생긴다.
- 등 대신 측면이나 앞면이 보인다.
- 확대해도 존재하지 않는 정보가 복원되지는 않는다.

따라서 OCR을 상시 가능한 센서로 보면 안 된다.

### 8.2 권장 방식

OCR은 매 프레임 답을 내는 기능이 아니라 **트랙 전체에서 번호 증거를 누적하는 기능**으로 설계한다.

```text
player tracklet
  ↓
등이 보이는 프레임 선택
  ↓
선명도·크기·가림 정도 평가
  ↓
좋은 프레임만 번호 인식
  ↓
여러 프레임의 후보 통합
  ↓
로스터와 비교
```

근경에서 한 번 식별한 뒤 원경에서는 위치와 track continuity로 ID를 유지하는 방식이 현실적이다.

## 9. 파노라마 분석과 카메라별 분석

### 9.1 파노라마 우선 방식

```text
Camera A + Camera B
        ↓
분석용 파노라마 프레임
        ↓
검출·tracking
```

장점:

- 분석 입력이 하나다.
- 카메라 간 중복 객체 통합이 필요 없다.
- 소프트웨어 구조가 이해하기 쉽다.

단점:

- 리샘플링과 스티칭 손실
- 거대한 중간 파일 문제
- 원본 해상도 활용 제한
- seam 문제

### 9.2 카메라별 분석 방식

```text
Camera A → 검출·tracking → pitch coordinate ┐
                                             ├→ 통합
Camera B → 검출·tracking → pitch coordinate ┘
```

장점:

- 원본 화질 활용
- 병렬 처리 용이
- 대용량 파노라마 파일 불필요
- ROI와 타일 처리에 유리

단점:

- 카메라 간 중복 제거
- track handoff
- 시간 동기화
- 관측 신뢰도 통합

### 9.3 현재의 결론

장기적으로는 카메라별 분석이 더 합리적일 가능성이 높다.  
다만 MVP에서는 복잡도를 관리하기 위해 다음과 같은 하이브리드 접근도 가능하다.

- 기본 전역 분석: 저해상도 파노라마 또는 전체 축소본
- 정밀 분석: 카메라별 원본 타일
- 최종 시청 영상: 필요할 때만 스티칭

## 10. 데이터 구조와 모듈 경계

검출기, tracker, OCR 모델을 교체하더라도 이후 모듈이 같은 형식을 읽도록 공통 관측 포맷을 정의하는 것이 중요하다.

```json
{
  "timestamp": 2534.20,
  "camera_id": "cam_left",
  "local_track_id": 187,
  "class": "player",
  "bbox": [x1, y1, x2, y2],
  "ground_point": [px, py],
  "pitch_position": [42.8, 17.3],
  "confidence": 0.91,
  "team_candidate": "home",
  "visibility": 0.76
}
```

권장 모듈 구조:

```text
CaptureSync
- 오디오 추출
- offset / drift 계산
- 공통 시간축

CameraGeometry
- lens calibration
- pitch calibration
- pixel ↔ pitch transform

Perception
- player/referee/ball detector
- tile scheduler
- local tracker

ObservationFusion
- 전체 프레임/타일 결과 통합
- 카메라 간 중복 제거
- confidence fusion

Identity
- tracklet association
- OCR evidence
- roster mapping
- user correction

Applications
- radar
- virtual PTZ
- stitching
- tactical analytics
- event analytics
```

## 11. Radar의 역할

Radar는 최종 분석 그 자체라기보다 **관측 결과의 중간 표현**이다.

Radar만으로 비교적 직접 얻을 수 있는 것:

- 팀 폭과 깊이
- 수비 라인
- 선수 밀집도
- 경기장 구역별 인원 수
- 짧은 시간의 이동 궤적

Radar만으로 직접 알기 어려운 것:

- 왜 공간이 열렸는가
- 누가 마크를 끌어냈는가
- 압박이 언제 깨졌는가
- 어떤 패턴이 반복되는가
- 특정 선수의 전술적 의도

따라서 radar는 전술 분석의 입력이자 virtual PTZ 제어의 기반으로 보는 것이 적절하다.

## 12. Virtual PTZ

현재처럼 공을 항상 화면 중앙에 놓는 방식은 단순하지만 축구 영상 구도로는 자주 부자연스럽다.

좋은 카메라 구도는 현재 공뿐 아니라 다음 장면을 고려해야 한다.

- 공의 이동 방향
- 공격 방향
- 관련 선수 군집
- 수비 라인
- 침투 공간
- 골문과 페널티지역
- 전환 속도

### 12.1 PTZ 목표

```text
radar state
    ↓
경기 상태 추정
    ↓
관심 영역 계산
    ↓
목표 PTZ pose
    ↓
스무딩·속도 제한
    ↓
virtual camera output
```

### 12.2 규칙 기반 MVP

초기에는 학습 모델보다 규칙 기반이 적절하다.

- 공이 빠르게 움직이면 앞쪽 여백 증가
- 역습 상황에서는 zoom out
- 측면 공격에서는 페널티지역 쪽 여백 확보
- 세트피스에서는 공보다 선수 군집 중심
- 공 신뢰도가 낮으면 선수 분포와 최근 공 위치 사용
- pan과 zoom에 dead zone, 최대 속도, 가속도 제한 적용

이 기능은 실제 선수 ID가 필요하지 않기 때문에 perception 파이프라인의 첫 실용 응용으로 적합하다.

## 14. 데이터 수집과 커스텀 학습

현재 PitchWatch의 검수 UI와 track timeline은 그대로 학습 데이터 생산 도구로 활용할 수 있다.

```text
기존 모델로 자동 검출
        ↓
사용자가 수정
        ↓
수정 결과를 라벨로 저장
        ↓
실패 사례 중심으로 재학습
        ↓
새 모델로 다시 분석
```

### 라벨링 우선순위

모든 프레임을 균일하게 라벨링하지 않는다.

- 원경 선수 누락
- 심판 오분류
- 선수 밀집 구간
- 역광·그늘
- 흰색 라인과 유니폼 겹침
- 경기장 밖 사람
- 벤치 인원
- 타일 경계 객체
- 모션 블러
- 누워 있거나 일부만 보이는 선수
- 작은 공과 유사한 오검출 대상

### 데이터 분할

연속 프레임을 무작위로 나누지 않고 경기 단위로 분할한다.

```text
Train: 경기 A, B, C, D
Validation: 경기 E
Test: 다른 날짜·경기장·유니폼의 경기 F
```

같은 경기의 유사 프레임이 train과 validation에 동시에 들어가면 성능이 과대평가될 수 있다.

## 15. 대용량 영상 처리

오픈소스 로컬 처리 모델에서는 서버 저장비 문제는 줄지만, 사용자 로컬 환경에서 저장공간과 처리시간 문제는 여전히 크다.

권장 원칙:

- 8K 원본은 정보 저장소로 취급
- 분석은 축소본과 타일을 조합
- 전체 8K 파노라마는 기본적으로 만들지 않음
- 필요한 구간만 고해상도 렌더링
- 시청용 출력은 1080p 또는 4K
- 분석 결과는 좌표·tracklet·event 데이터로 저장
- 최종 영상은 필요할 때 재생성

```text
Stitch on demand
Render only what is viewed
Store decisions rather than duplicate video
```

## 16. 오픈소스 공개 시 고려사항

오픈소스 모델에서는 사용자가 소프트웨어를 내려받아 로컬에서 처리한다.

장점:

- 원본 영상이 외부 서버에 올라가지 않는다.
- 구독 없이 계속 사용할 수 있다.
- 저장 정책을 사용자가 결정한다.
- 카메라와 rig를 자유롭게 선택할 수 있다.
- 연구와 검증이 가능하다.
- 커뮤니티가 새로운 rig·카메라 프로파일을 추가할 수 있다.

오픈소스 프로젝트의 핵심 자산은 단순 코드보다 다음이 될 수 있다.

- 표준 rig 규격
- 카메라 프로파일
- calibration 포맷
- 공통 관측 데이터 포맷
- 학습 데이터 제작 도구
- 검수 UI
- 플러그인 API
- 재현 가능한 처리 파이프라인

## 18. 최종 정리

PitchWatch의 핵심 기반은 다음 세 가지다.

```text
시간 동기화
    ↓
공간 calibration
    ↓
선수·심판·공 perception
```

그 이후의 radar, virtual PTZ, stitching, 팀 전술 분석, 선수별 통계는 모두 이 기반 위에 올라간다.

현재 단계에서 가장 중요한 질문은 다음이다.

> 정해진 카메라와 경기장 조건에서 선수·심판·공을 얼마나 안정적으로 검출하고, 얼마나 긴 tracklet으로 유지하며, 얼마나 적은 수동 수정으로 신뢰 가능한 경기장 좌표 데이터를 만들 수 있는가?

커스텀 YOLO와 타일 분석은 이 기반을 크게 개선할 가능성이 있다.  
다만 완전 자동 선수 식별과 전술 해석은 별도의 상위 문제로 남는다.

따라서 개발의 우선순위는 분석 기능을 계속 추가하는 것보다, **반복 가능한 동기화·calibration·perception 파이프라인과 객관적인 평가 체계를 먼저 만드는 것**이 적절하다.

### 총평

방향이 정확하며, "완전 자동 분석이 아니라 신뢰 가능한 관측 스트림"
프레임(1·18장)은 실제 개발 궤적과 독립적으로 수렴한다. 문서에서 가장
값진 항목은 13장의 운영 지표 — **"90분 경기 하나에 사람이 몇 번
수정해야 쓸 만해지는가."**

### 이미 구현돼 있는 항목 (문서 대비 현황)

- **0단계 동기화**: 오디오 상관 + 호각 anchor + 경기 시계 모델 — 구현.
- **1단계 캘리브**: 랜드마크 UI, 재투영 검증·잔차 표시, 발 접점 사용,
  회전캠(rotcam) 자기캘리브까지 — Phase 1 은 사실상 완료 단계.
- **원근 적응형 타일**(6장): 원경 네이티브 타일 + 미니 트래커(tid
  800001+) 구현 (devlog 077/078). 실측: 원경 검출 2.3배, 전체 검출의
  ~48% 기여 (#11).
- **OCR 증거 누적**(8.2): 트랙릿별 다프레임 크롭 → 신뢰도 가중 투표 —
  이미 구현됨.
- **검수 UI = 라벨링 도구**(14장): 편집 데이터는 사이드카에 축적 중 —
  학습 포맷 내보내기만 남음.
- radar=중간 표현(11장), 규칙 기반 PTZ+스무딩(12장) — 현 구조와 일치.

### 반론·뉘앙스

1. **카메라별 분석이 장기적으로 합리적(9장)** — 절반만 동의. 실측상
   원경 병목은 리샘플링 손실이 아니라 검출 입력 크기였고, 파노라마 위
   네이티브 타일이 문서의 하이브리드(9.3)를 이미 달성. 파노라마는
   시청·검수 산출물로 어차피 필요하다.
2. **커스텀 YOLO(5장)** — 방향은 맞지만 순서: **평가 하네스 없이
   파인튜닝하면 개선을 측정할 수 없다**. 지표 체계 → 라벨 내보내기 →
   파인튜닝 순이 적절.
3. **"전체 파노라마는 만들지 않음"(15장)** — 8K 가정의 결론. 현 6K
   체계에선 파노라마 + 스크럽 프록시 조합이 저장·시청·검수 모두에서
   유효. 8K 전환 시 재검토.

auto-level 발산(효창·언남 실증, devlog 081)이 파이프라인 신뢰성을
좌우하나 문서에 없음. 스티칭 시작 시 수평 프리뷰 게이트는 구현됨
