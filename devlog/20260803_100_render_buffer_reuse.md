# 100 — 미설명 13ms 의 정체: 페이지 폴트. 버퍼 재사용으로 render 3.3배

2026-08-03. devlog 098 에서 `render()` 의 단계 합계와 전체가 13ms 안 맞는다고
적었다. 규명했다 — **프레임마다 새로 할당하는 41MB 의 페이지 폴트**였고,
그게 첫 쓰기 단계에 얹혀 보이지 않았다. 고치니 render 가 다시 두 배 빨라졌다.

## 규명 — 측정 방법이 숨기고 있었다

098 의 프로파일은 각 단계를 **따로 루프** 돌려 쟀다. 그러면 같은 버퍼를
반복 사용해 이미 매핑된 상태라 폴트 비용이 안 잡힌다. **한 번의 render 안에서
순서대로** 재니 드러났다:

| 단계 | 개별 루프 측정 | 문맥 내 측정 |
|---|---|---|
| **복사 L** | 2.21ms | **11.33ms** |
| 복사 R | 2.18ms | 5.25ms |
| np.empty | 0.02ms | 1.65ms |

`np.empty` 자체는 공짜가 맞다 (41MB 할당+터치 실측 0.05ms). **비용은 처음
쓸 때** 발생하고, 그래서 출력 버퍼에 처음 쓰는 "복사 L" 이 전부 뒤집어썼다.

프레임당 할당량: 워프 결과 2×20.8MB + LUT 결과 2×20.8MB + 출력 41MB
= **약 83MB**.

## 고친 것 — 워프 버퍼 상주 + 출력에 직접 쓰기

```python
wl = self.warp(img_l, 0, dst=self._warp_buf[0])   # 상주 버퍼
wr = self.warp(img_r, 1, dst=self._warp_buf[1])
out = np.empty(...)                                # 출력은 매번 새로
cv2.LUT(wl[:, :x0], self._lut_l, dst=out[:, :x0])  # 최종 버퍼에 직접
cv2.LUT(wr[:, x1 - x0:], self._lut_r, dst=out[:, x1:])
```

중간 LUT 배열과 조립 복사가 통째로 사라진다. `cv2.LUT` 이 **비연속 슬라이스**
(`out[:, :x0]`, 행 스트라이드 `out_w*3`)를 `dst=` 로 받는 것을 확인했다.

### 출력 버퍼는 일부러 재사용하지 않았다

두 변형을 나눠 쟀다:

| | WSL | Windows |
|---|---|---|
| 워프 버퍼만 재사용 | +52.7% | +43.2% |
| 출력 버퍼까지 재사용 | +56.5% | +51.7% |

**출력까지 재사용하면 4~8% 를 더 얻지만 쓰면 안 된다.** `export_pano` 는
프레임을 큐(maxsize=4)에 넣고 별도 스레드가 인코더로 보낸다 — 반환 버퍼를
재사용하면 **큐에 든 앞 프레임을 덮어쓴다.** 워프 버퍼는 외부로 나가지
않으므로 안전하다.

출력은 **비트 동일**(최대차 0). 184건 통과.

## 효과

렌더 단계 (5976×2306, 120프레임):

| | 원래 | LUT (098) | **+ 버퍼 재사용** | 누적 |
|---|---|---|---|---|
| WSL | 58.0ms / 17.24fps | 35.2ms / 28.42fps | **17.6ms / 56.69fps** | **3.3×** |
| Windows | 80.7ms / 12.38fps | 42.5ms / 23.52fps | **24.7ms / 40.55fps** | **3.3×** |

코어: WSL 2.21 → 4.14 → **6.95**, Windows 2.07 → 3.62 → **6.04**.

종단 (3분 구간 5,394프레임, **조건당 2회**):

| | 이전 | 이후 | stitch 단계 | 편차 |
|---|---|---|---|---|
| WSL | 22.7 fps | **27.5 fps** | 288.6 → 247.1s (+14.4%) | **0.7%** |
| Windows | 15.7 fps | ~17.8 fps | 469.2 → 400.6s (+14.6%) | 2.3% |

> Windows 는 export 로그를 못 잡아 stitch 단계에서 정합 97s 를 빼 역산했다.
> stitch 단계 값(직접 측정)끼리 비교하면 양쪽 다 **+14.5%** 다.

편차가 0.7~2.3% 로 devlog 099 에서 본 7.7% 보다 훨씬 작다. 그때는 다른
작업이 섞였던 것으로 보인다 — **반복 측정을 기본으로 삼는다.**

## 병목이 render 를 떠났다

프레임당 (버퍼 재사용 후):

| | decode | render | 변환 | pipe |
|---|---|---|---|---|
| WSL | 16.6ms (60fps) | 17.6ms (57fps) | 2.9ms | **25.4ms (39fps)** ← |
| Windows | **26.8ms (37fps)** ← | 24.7ms (40fps) | 3.8ms | 6.6ms (145fps) |

- **WSL 은 파이프가 병목이다.** devlog 099 에서 I420 이 +47% 였던 이유가
  이것이고, 이제 더 줄이려면 파이프 자체를 손봐야 한다
- **Windows 는 디코드가 병목이다.** 여기서 NVDEC 이 직접 먹힌다
  (devlog 093·094 의 `ChapteredGpuReader`)

다만 종단 27.5fps 는 최저 단계(39fps)에도 못 미친다 — 3단 파이프라인의
스레드 경합/CPU 포화가 남아 있다는 뜻이다. 총 CPU 가 프레임당 WSL ~250ms
로 8코어 기준 32fps 상당이라, **이제 개별 단계가 아니라 전체 CPU 예산이
한계**에 가깝다.
