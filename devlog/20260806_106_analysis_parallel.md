## 왜 2병렬이 공짜인가

**단독일 때 SM 이 이미 52% 인데 2병렬에서도 50% 다.** `utilization.gpu` 는
용량이 아니라 "커널이 돌던 시간 비율"이라, 단독 분석은 GPU 를 절반은
놀리고 있다는 뜻이다 (커널 사이 공백·CPU 전후처리·동기화). 두 번째
프로세스가 그 틈을 메운다.

3병렬에서 SM 69%, 4병렬 78% 로 올라가며 이득이 줄어든다. VRAM 은 4병렬에도
6.7GB/11.3GB 로 여유가 있어 **한계는 VRAM 이 아니라 SM** 이다.

## ⚠️ 4병렬 측정은 오염됐다

4번째로 넣은 `pano_0374` 가 **CPU 디코드로 폴백**했다 (1.75~2.00 코어).
h264 6348px 인데 **NVDEC 의 h264 디코드 상한이 4096px** 이라서다 —
devlog 090 에서 NVENC 인코딩에 걸렸던 것과 같은 하드웨어 한계다
(hevc 는 8192px).

즉 4병렬 수치는 "3개 NVDEC + 1개 CPU" 라, 순수 4병렬은 조금 더 나을 수
있다. 다만 3→4 이득이 이미 작아 결론은 안 바뀐다.

### 곁들여 고친 버그

폭 한계를 미리 걸러 OpenCV assertion 에러를 막으려 했는데, **FOURCC 표기를
잘못 읽어 hevc 파노라마까지 NVDEC 을 건너뛰었다.** 이 빌드(opencv 4.13)는
컨테이너 태그(`hvc1`)가 아니라 **코덱 이름 그대로(`hevc`)** 를 준다.
`_is_hevc_tag()` 로 분리하고 표기 변종을 테스트로 고정했다 (16건 통과).

**운영상 함의:** 구 파노라마는 h264 6348px 라 NVDEC 을 못 탄다. 재분석
대상 중 hevc 로 인코드된 것만 이득을 본다.

## 권고 — 재분석 배치는 3병렬

| | 8편 배치 환산 |
|---|---|
| 순차 (현행) | 기준 |
| 2병렬 | **1.93배** |
| **3병렬** | **2.53배** |
| 4병렬 | 2.75배 (오염) |

100시간+ 배치가 3병렬이면 **40시간 아래**로 떨어진다. 4병렬은 +9% 를 위해
메모리·안정성 여유를 깎는 셈이라 3을 권한다.

> **⚠️ 정정 (devlog 107):** 아래 문단은 틀렸다. CPU 디코드로도 3병렬이
> 잘 된다 (32.91fps, 총 5.4/8코어). 디코드 **단독** 벤치를 외삽한 오류다 —
> 분석 중 디코드는 분석 페이스로만 돌아 ~0.9코어다. NVDEC 이득은
> 병렬성을 여는 게 아니라 **+9.1%** 다.
