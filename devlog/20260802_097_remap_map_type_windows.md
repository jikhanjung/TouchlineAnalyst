# 097 — Windows 스티칭이 느린 진짜 이유: remap 맵 타입

2026-08-02. devlog 096 이 "Windows 용 opencv-python 휠의 remap 이 CPU 를 48%
더 쓴다"까지 밝혔다. 다른 빌드를 써보려다 **빌드가 아니라 맵 타입이 문제**임을
찾았다. 코드 한 줄 수준의 변경으로 Windows 렌더가 **11% 빨라지고 CPU 20%
줄었다**.

## 발단 — 빌드를 바꿔보려 했다

Windows 에서 다른 OpenCV 빌드를 테스트했다. 결과는 **전부 현행보다 나쁘거나
비슷**했다. 그런데 마이크로벤치를 맵 타입별로 나눠 재다가 이게 나왔다.

`cv2.remap` 단독, 5976×2306 출력, 40회:

| 빌드 / 맵 타입 | float32 | CV_16SC2 |
|---|---|---|
| **WSL 5.0.0** | 13.58ms | **13.74ms** |
| Windows 5.0.0 | **15.12ms** | **23.21ms** ← 현행 조합 |
| Windows 4.13 (PyPI) | 21.00ms | 20.77ms |
| Windows 4.13 (conda-forge) | 22.28ms | 23.70ms |

**고정소수점 맵이 빠르다는 통념이 Windows 빌드에선 정반대다** — float32
대비 **1.54배 느리다**. Linux 빌드에선 둘이 사실상 동등(2% 차)하다.

`Renderer._rebuild_cropped_maps` 가 `convertMaps(..., CV_16SC2)` 를 쓰고
있었으니, **하필 Windows 에서 가장 느린 조합**을 골라 쓰고 있었던 셈이다.

## 실측 — 실제 렌더

| | fps | ms/프레임 | CPU/프레임 |
|---|---|---|---|
| Windows, CV_16SC2 (현행) | 12.38 | 80.7 | 182.8ms |
| **Windows, float32** | **13.78** | **72.6** | **145.8ms** |
| WSL, CV_16SC2 (현행) | 17.24 | 58.0 | 128.0ms |
| WSL, float32 | 16.88 | 59.2 | 139.0ms |

Windows **+11%, CPU −20%**. WSL 은 −2%. 그래서 **플랫폼별로 고른다.**

적용 후 단계 벤치로 확인: Windows render **80.2 → 72.9ms/프레임**
(12.47 → 13.71fps), CPU 2.30 → 2.07 코어.

## 화질은 오히려 좋아진다

고정소수점 맵은 좌표를 **1/32 픽셀로 양자화**한다. float32 는 그 손실이
없다. 두 경로 출력 차이는 PSNR **59.7dB**, 평균차 0.066, 최대차 4 —
무시할 수준이고 방향은 float32 가 정확한 쪽이다.

## 바꾼 것

`render.py` 에 `USE_FIXED_MAPS` — 기본값은 **win32 면 float32, 그 외는
CV_16SC2**. `PYSTITCH_FIXED_MAPS=1/0` 으로 강제 가능.

`tests/test_perspective_widen.py::test_map_type_paths_agree` — 두 경로가
갈라지면 **OS 마다 다른 파노라마가 나오므로** 합성 프레임으로 일치를 지킨다
(PSNR > 35). 전체 184건 통과.

## 균형 잡기

| 개선 | 효과 | 비용 |
|---|---|---|
| **WSL 로 스티칭 이전** | **+66%** | 코드 0 |
| 맵 타입 (이 변경) | Windows +11% | 코드 몇 줄 |
| 다른 OpenCV 빌드 | **없음** (4.13·conda-forge 모두 열세) | — |

WSL 이전이 여전히 압도적이다. 맵 타입 변경은 그와 별개로 거의 공짜라
같이 취하면 된다 — Windows GUI 내보내기에도 그대로 먹힌다.

## 남은 의문

맵 타입을 고쳐도 Windows render 72.9ms vs WSL 58.0ms 로 **여전히 26% 느리다.**
IPP(2026.0.0)·dispatch 세트·baseline 이 두 빌드에서 동일하고 CI 타임스탬프도
같은 날인데 그렇다. 남은 후보는 MSVC 코드젠과 ConcRT 병렬 프레임워크인데,
render 가 양쪽 다 2.0~2.2 코어를 쓰므로 스케줄링보다 코드젠 쪽이 유력하다.
더 파려면 OpenCV 를 직접 빌드해 비교해야 해서 여기서 멈춘다.
