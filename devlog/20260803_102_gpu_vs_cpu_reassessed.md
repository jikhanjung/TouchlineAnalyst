# 102 — GPU 상주 경로 재평가: CPU 가 앞질렀다 (스티칭 최적화 종료)

2026-08-03. "GPU 로 가면 분석과 SM 경합" 이라는 내 논거는 과했다 — 헤드리스
`process_pair` 는 **스티칭 → 분석을 순차로** 돌리므로 기본 워크플로에
경합이 없다. 그런데 그 사이 셈이 뒤집혔다. 오늘의 CPU 최적화가 GPU
프로토타입을 앞질렀다.

## 현재 (5976×2270, 같은 소재)

| 경로 | fps | CPU 코어 |
|---|---|---|
| GPU 프로토타입 | 23.72 | **0.77** |
| **WSL CPU** | **27.5** | ~6 |
| Windows CPU | ~19.9 | ~6 |

devlog 096 의 "GPU 1.39배" 는 CPU 경로가 17.1fps 이던 시절 비교다. 오늘
넣은 세 가지(맵 타입 float32 · 게인 LUT · 버퍼 재사용)가 CPU 를 3.3배로
만들면서 순위가 바뀌었다. 그 최적화들은 GPU 프로토타입에 적용되지 않는다 —
자체 GPU 루프라 무관하다.

- **WSL: GPU 로 가면 13% 손해**
- **Windows: GPU 가 19% 이득**

## GPU 경로에 남은 것

처리량이 아니라 **CPU 점유 0.77코어 vs ~6코어**다. 이게 의미 있는 경우:

- 스티칭 2편 동시 실행 (CPU 경로는 코어를 다 써서 불가)
- 스티칭 중에도 머신을 쓸 수 있음
- 분석을 겹쳐 돌릴 때 — SM 은 59+52=111% 로 넘치지만, 스티칭 CPU 가
  0.77코어면 분석의 CPU 디코드에 코어를 양보할 수 있다

그리고 **프로토타입은 아직 순차 루프**다. CPU 경로처럼 3단 파이프라인으로
겹치면 23.72 를 넘을 여지가 있고, NV12 일관 경로로 가면 색변환 차이
(PSNR 40.6dB)도 함께 해결된다. **둘 다 미측정이다.**

## 결정 — 스티칭 최적화는 여기서 접는다

오늘의 성과 (같은 소재·같은 출력):

| | 종단 fps | `pano_0002` 환산 |
|---|---|---|
| Windows 최초 | 9.6 | 3.38시간 |
| Windows 현재 | ~19.9 | 1.63시간 |
| WSL 최초 | 17.1 | 1.90시간 |
| **WSL 현재** | **27.5** | **1.18시간** |

최초 Windows 3.38시간 → 현재 WSL 1.18시간, **2.86배**. 여기서 더 가려면
GPU 프로토타입 파이프라인화(반나절, 결과 불확실)가 필요한데, **재분석
배치 100시간+ 에 비하면 우선순위가 낮다.**

## 이 일련의 작업에서 배운 것

- **개별 단계 벤치는 파이프라인 종단을 예측하지 못한다** (devlog 101).
  CPU 포화 상태에선 가장 느린 단계가 아니라 총 CPU 예산이 구속 조건이다
- **개별 루프 측정은 페이지 폴트를 숨긴다** (devlog 100). 같은 버퍼를
  반복 쓰면 이미 매핑돼 있다 — 문맥 내에서 재야 한다
- **반복 없는 A/B 는 5% 대 차이를 못 가린다** (devlog 099). 이 머신
  편차가 조건에 따라 0.4~7.7% 다
- **역산하지 말고 로그를 남길 것** (devlog 101). 정합 시간을 97초로
  가정해 Windows fps 를 잘못 냈다 (실제 119초)
- **통념을 실측으로 확인할 것** — 고정소수점 맵이 빠르다(Windows 에선
  반대), NVDEC 이 디코드를 공짜로 만든다(전송이 남으면 6% 뿐)
