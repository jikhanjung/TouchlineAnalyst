# 103 — 원경 tid 가 수동 검출 네임스페이스를 침범하고 있었다

2026-08-03. TODOs #1(원경 트랙릿 파편화) 정량화를 시작하자마자 버그가 나왔다.
**`_FarTracker` 가 상한 없이 tid 를 할당해 수동 검출 영역을 덮어쓰고 있었다.**
튜닝보다 먼저 고쳤다.

## 발견 — 0392 실측

`scripts/tracklet_diag.py` 를 새로 만들어 `.analysis.cache.json` 만으로
(527MB 원본을 안 열고) 정량화했다.

| 네임스페이스 | 개수 | 범위 |
|---|---|---|
| ByteTrack | 88,927 | 7 ~ 316,425 |
| far | **100,000** | **800001 ~ 900000** (가득) |
| 900001+ | **29,952** | **900001 ~ 929952, 구멍 0개** |

`_FarTracker.next_id` 는 800001 에서 시작해 **상한 검사가 없었다.**
네임스페이스가 정확히 10만 개인데 0392(5.6시간)는 원경 트랙을
**129,952개** 만들었다. 초과분 29,952개가 900001+ 로 연속해 흘러넘쳤다 —
구멍이 하나도 없어 오해의 여지가 없다.

## 왜 나쁜가

900001+ 는 **수동 검출(extra)** 영역이고 GUI 가 실제로 그렇게 취급한다:

- `ptz_tab.py` 장외 필터에서 **면제** — 파편 3만 개가 필터를 우회
- 메뉴·표시에서 수동 검출로 다뤄지고 `선수 #{tid-900000}` 으로 이름 붙음
  → **"선수 #1 ~ #29952"** 가 생긴다
- `.ptz.json` 의 사용자 편집(역할·번호·병합)이 tid 로 연결되므로,
  편집이 있는 영상이면 **엉뚱한 트랙에 편집이 붙는다**

0392 의 `.ptz.json` 은 venue 시딩뿐이라 실제 손상은 없었다. 다만 이 영상은
`--far-augment` 대상 목록에 있고, 편집이 있는 다른 영상도 같은 조건이면
같은 일이 난다.

## 고친 것

**1. 네임스페이스를 10배로 넓히고 코어에 단일 출처로 선언**

```python
FAR_TID_BASE = 8_000_001     # 원경 (100만 개 — 0392 사용량의 7.7배)
FAR_TID_MAX  = 8_999_999
EXTRA_TID_BASE = 9_000_001   # 수동 검출
```

**2. 판별식을 함수로** — 하드코딩된 `tid >= 900000` 비교를 전부 교체했다.
구 사이드카 호환(far 800001~900000, 수동 900001~999999)을 안에 담았다.

```python
is_far_tid(tid) / is_extra_tid(tid) / extra_tid_number(tid)
```

GUI 쪽 교체 지점: `_next_extra_id` 초기값·재계산, 장외 필터 면제 조건,
컨텍스트 메뉴 분기, 표시 번호. `_next_extra_id` 재계산은
`max([*ids, EXTRA_TID_BASE - 1]) + 1` 로 바꿔 **구 사이드카에 900001+ 가
있어도 새 id 는 항상 새 범위에서** 뽑는다.

**3. 소진 가드** — 범위가 차면 `update()` 가 해당 검출 자리에 `None` 을
넣고 호출부가 건너뛴다. 첫 회에 한 번만 로그한다.

> 검출을 버리는 게 손해지만, **넘쳐서 사용자 편집을 덮어쓰는 것보다 낫다.**
> 그리고 소진 자체가 "파편화 튜닝이 필요하다"는 신호다.

## 곁들여 — 파편화의 실체가 TODOs 설명과 다르다

| | 개수 | 관측 중앙값 | 수명 중앙값 | 단발 |
|---|---|---|---|---|
| **근경 (ByteTrack)** | 88,927 | **60프레임 (2.0초)** | 8.51초 | **6.4%** |
| **원경 (far)** | 129,952 | **9프레임 (0.3초)** | 1.30초 | **31.7%** |

TODOs 의 "길이 중앙값 27프레임 ≈ 0.9초" 는 **전체 중앙값**이었다.
쪼개 보면 **근경은 건강하고(수명 8.5초, 단발 6.4%) 원경만 심각하다** —
원경은 **셋 중 하나가 단발**(한 번 보이고 끝)이다.

근경이 멀쩡한 건 `tracker_pano.yaml` 의 `with_reid: True` 가 일하고 있다는
뜻이기도 하다. 원경은 ReID 경로를 아예 안 탄다 — 4K 에서 원경 선수는
약 36px 라 외형 특징이 안 나온다 (devlog 092). 최근접 연결이 맞는 선택이고,
개선은 반경·만료·검출 안정성 쪽에서 찾아야 한다.
