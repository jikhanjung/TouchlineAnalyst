# 098 — render 단계 프로파일: 진짜 병목은 게인 곱셈이었다

2026-08-02. devlog 097 에서 맵 타입을 고쳤는데도 Windows/WSL 격차가 25% 남아
"메모리 바운드 구간에 몰려 있을 것"이라고 가정했다. **틀렸다.** `render()` 를
단계별로 쪼개 재니 훨씬 큰 게 나왔다 — **단일 스레드 게인 곱셈**.

`cv2.multiply` → `cv2.LUT` 로 바꿔 **렌더 +65~72%, 종단 +29~38%**. 출력은
**비트 동일**이라 화질 트레이드오프가 없다.

## 단계별 프로파일 (5976×2306, 40회)

| 단계 | WSL | 코어 | Windows | 코어 |
|---|---|---|---|---|
| warp L (remap) | 5.94ms | **7.28** | 8.21ms | 6.04 |
| warp R (remap) | 5.76ms | **7.59** | 8.61ms | 5.67 |
| **multiply ×2 (게인)** | **28.32ms** | **1.00** | **39.26ms** | **0.98** |
| np.empty (출력 할당) | 0.02ms | — | 0.02ms | — |
| 조립 복사 L/R | 4.39ms | 1.0 | 5.04ms | 0.93 |
| blendLinear (심밴드) | 0.46ms | 2.73 | 0.66ms | 1.18 |
| render() 전체 | 59.56ms | 2.20 | 73.71ms | 2.11 |

**remap 은 이미 7코어로 잘 돌고 있었다.** 문제는 그 옆의 게인 곱셈이
혼자 1코어로 remap 두 개 합의 **2.4배**를 쓰고 있던 것이다. render 가
전체적으로 2.2코어밖에 못 쓰던 이유가 이것이다.

097 에서 remap 을 고친 게 헛일은 아니지만, **애초에 remap 이 병목이 아니었다.**
단계별로 쪼개 재지 않았으면 계속 못 봤을 것이다.

부수적으로 097 의 가설도 정정된다 — 남은 격차는 특정 구간에 몰려 있지 않고
**전 단계에 고르게 ~40%** 퍼져 있다.

## 왜 LUT 인가

게인은 **채널별 스칼라 곱**이다. uint8 입력이면 값이 256가지뿐이므로
256엔트리 테이블로 미리 계산할 수 있다. `cv2.LUT` 는 병렬화된다.

| | cv2.multiply | cv2.LUT | 배속 |
|---|---|---|---|
| WSL | 14.86ms (0.99코어) | **2.74ms (7.20코어)** | 5.4× |
| Windows | 19.51ms (0.96코어) | **3.07ms (5.72코어)** | 6.4× |

**비트 동일하다.** 게인 조합 **1000건**(포화·극단값 포함)으로 검증했다 —
양쪽 다 round-half-even + 포화라 정확히 같은 값이 나온다. 근사가 아니다.

## 효과

렌더 단계:

| | 전 | 후 | 코어 |
|---|---|---|---|
| WSL | 58.0ms / 17.24fps | **35.2ms / 28.42fps** (+65%) | 2.21 → **4.14** |
| Windows | 72.9ms / 13.71fps | **42.5ms / 23.52fps** (+72%) | 2.07 → **3.62** |

종단 스티칭 (3분 구간, 5,394프레임, 5976×2270 고정):

| | 전 | 후 | |
|---|---|---|---|
| WSL | 17.1 fps | **22.0 fps** | **+29%** |
| Windows | 10.3 fps | **14.2 fps** | **+38%** |

종단이 렌더 단계보다 덜 오르는 건 예상대로다 — LUT 는 wall 을 5배 줄이는
대신 **CPU 를 34% 더 쓴다**(7코어 활용). 3단 파이프라인에서 디코드·파이프
스레드와 코어를 다투므로 이득이 희석된다.

## 병목이 이동했다

프레임당 (LUT 적용 후):

| | decode | render | 변환 | pipe |
|---|---|---|---|---|
| WSL | 18.0ms (55fps) | **35.2ms (28fps)** | 3.6ms | **27.5ms (36fps)** |
| Windows | 28.2ms (35fps) | **42.5ms (23fps)** | 4.3ms | 6.9ms (145fps) |

**WSL 은 pipe(36fps)가 render(28fps)에 바짝 붙었다.** render 를 더 빠르게
하면 다음 병목은 파이프다 — devlog 096 에서 "WSL 파이프가 Windows 의 1/4
속도"라고 기록한 그 지점이 곧 전면에 나온다. Windows 는 아직 render 가
명확한 상한이다.

## 바꾼 것

- `render.py`: `gain_lut()` 추가, `gain_l`/`gain_r` 을 **프로퍼티**로 만들어
  대입 시 LUT 를 함께 생성. `render()` 는 LUT 만 쓴다
- `render_pano()`(저해상도 1회용 경로)는 float 연산이라 그대로 뒀다
- 전체 184건 통과
