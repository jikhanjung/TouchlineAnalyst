# 101 — L·R 병렬 디코드: 단독 +22.6%, 종단 0% (되돌림)

2026-08-03. devlog 100 에서 "Windows 는 디코드가 병목(26.8ms, 37fps)"이라고
적고 개선을 시도했다. **단독 측정으로는 +22.6% 였지만 종단은 노이즈였다.**
되돌렸다. 그리고 100 에 적은 Windows fps 수치에도 오류가 있어 정정한다.

## 시도한 것들 (Windows, 두 스트림)

| 방법 | ms/프레임 | |
|---|---|---|
| ChapteredVideo 순차 (현행) | 42.89 | — |
| **L·R 스레드 병렬** | **35.00** | **+22.6%** |
| `CAP_PROP_N_THREADS` 2/4/8 | 42.1~42.6 | 효과 없음 |

`export.py` 의 reader 스레드는 `vid_l.read()` → `vid_r.read()` 로 순차였다.
`ThreadPoolExecutor(max_workers=1)` 로 R 을 겹쳐 읽도록 바꿨다.

## 종단은 노이즈 범위였다 (조건당 2회)

| | 전 | 후 | 편차(전/후) |
|---|---|---|---|
| Windows | 400.6s | 394.8s (**+1.4%**) | 2.3% / 0.5% |
| WSL | 247.1s | 251.0s (**−1.6%**) | 0.4% / 2.8% |

**양쪽 다 편차 안이다.** 되돌렸다 — 측정된 이득 없이 임계 경로에 스레드
복잡도(워커 수명, `ChapteredVideo` 비-스레드-안전 전제)만 늘린다.

## 왜 단독 측정이 빗나갔나

**3단 파이프라인이 이미 디코드를 렌더와 겹치고 있다.** 단독 벤치는 디코드가
8코어를 전부 쓸 수 있는 상황에서 쟀지만, 실제 파이프라인에서는 렌더가
6~7코어를 쓰는 중이다. 리더에 스레드를 하나 더 넣으면 **렌더와 코어를 다툴
뿐**이다.

일반화하면 — **파이프라인이 CPU 포화 상태면 개별 단계 벤치가 종단 이득을
예측하지 못한다.** devlog 100 에서 렌더 3.3배가 종단 14.5% 로 희석된 것도
같은 구조였고, 그때는 그래도 이득이 남았지만 여기서는 0 이었다.

따라서 100 의 "Windows 는 디코드가 병목" 이라는 표현도 부정확하다. 개별
단계로는 디코드가 가장 느리지만, 단계들이 겹쳐 도는 이상 **구속 조건은
가장 느린 단계가 아니라 총 CPU 예산**이다.

## 남은 디코드 개선안 (미적용)

ffmpeg 서브프로세스로 원시 프레임을 받는 경로도 재봤다 (한 스트림, 600프레임):

| | ms/프레임 |
|---|---|
| 소프트웨어 디코드 | 11.09 |
| `-hwaccel cuda` (NVDEC) | 10.47 |

**NVDEC 이 6% 밖에 안 낫다.** 이 경로의 병목이 디코딩이 아니라 **원시 프레임을
파이썬으로 옮기는 것**이기 때문이다 (12.4MB/프레임 ÷ 10.5ms = 1,180MB/s).

즉 "NVDEC 을 붙이면 디코드가 공짜"라는 기대는 **전송이 남는 경로에서는
성립하지 않는다.** devlog 093 에서 잰 18배(CPU)는 cudacodec 이 GpuMat 을
GPU 에 두고 전송을 안 했기 때문이다. 전송을 없애려면 remap 도 GPU 로 가야
하고, 그건 SM 59% 를 먹어 분석과 경합한다 (devlog 096).

## 정리

디코드 쪽은 **싼 개선이 남아 있지 않다.** 이제 스티칭을 더 빠르게 하려면
파이프라인 구조나 GPU 상주 경로 같은 큰 결정을 해야 한다. 오늘의 코드
개선(맵 타입·게인 LUT·버퍼 재사용)이 render 를 3.3배로 만든 것과 달리,
여기서부터는 공짜 점심이 안 보인다.
