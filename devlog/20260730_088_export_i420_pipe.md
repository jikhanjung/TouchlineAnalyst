# 088 — 인코더 파이프를 I420 직행으로 (스티칭 CPU 병목 ①)

2026-07-30. 0392 스티칭(9.7시간, 17.44fps) 중 실측한 병목을 근거로 가장
값싼 항목부터 손댔다. **실제 적용 효과 측정은 다음 영상부터** — 지금은
0392 분석/프록시가 기계를 점유하고 있어 벤치마크가 무의미하다.

## 실측 병목 (0392 export 중, 6022×2254 hevc_nvenc)

| 자원 | 사용률 | 판정 |
|---|---|---|
| GPU 컴퓨트 | 6% | 유휴 |
| NVENC | 42% | 여유 |
| **NVDEC** | **0%** | 미사용 (4K 두 스트림 소프트 디코드) |
| CPU | python 320% + ffmpeg 90% = **4.1/8코어** | 4코어 유휴 |
| 디스크 | ~11MB/s (283GB 읽기 + 112GB 쓰기 / 9.7h) | 병목 아님 |
| 원시 파이프 | 6022×2254×3B × 17.4fps ≈ **708MB/s** | 양쪽 memcpy |

즉 스티칭은 GPU·디스크·코어수 병목이 아니라 **싱글스레드 CPU 작업 +
파이프 복사**에 묶여 있다.

## 바꾼 것

`export.py` 가 `-pix_fmt bgr24` 로 원시 BGR 을 넘기고 ffmpeg 가 swscale 로
yuv420p 로 변환하고 있었다(ffmpeg 90% CPU 의 정체). I420 으로 직접 넘긴다:

- 파이프 **40.7MB → 20.4MB/프레임** (708 → 354MB/s)
- ffmpeg 는 색변환을 안 하고 NVENC 제출만 → **~0.9코어 회수**
- 변환은 **writer 스레드**에서 (원래 write 만 하며 놀고 있었고, cv2 가 GIL 을
  놓으므로 메인 스레드의 렌더와 실제로 겹친다). `tobytes()` 도 같이 옮겨
  렌더 스레드에서 직렬화 비용을 뺐다.
- `pipe_format(w, h)` 로 분리 — 홀수 해상도는 4:2:0 으로 표현 불가라
  `bgr24` 폴백 (가상 PTZ 출력이 홀수일 수 있다).

## 화질: swscale 과 같은가 (실측)

실제 파노라마 프레임(1806×676)으로 두 변환을 직접 비교:

| 평면 | 최대차 | 평균 | >2 비율 |
|---|---|---|---|
| Y | **1** | 0.49 | 0.000% |
| U | 7 | 0.64 | 0.328% |
| V | 8 | 0.63 | 0.115% |

둘 다 BT.601 제한범위(Y 20–235)로 **색행렬·레인지는 동일**하고, 차이는
크로마 서브샘플링 필터뿐. 원본 왕복 PSNR 은 **OpenCV 48.6dB vs swscale
44.5dB** — 손실이 없고 오히려 소폭 더 충실하다. 추가 `-color_range` 플래그
불필요.

(합성 이미지로는 최대차 111 이 나오는데, 64×48 에 포화 색블록·노이즈를 넣은
adversarial 내용이라 크로마 필터 차이가 과장된 것. 테스트는 실제 영상에
가까운 매끄러운 프레임으로 재도록 분리했다.)

## 검증

`tests/test_export_pipe.py` 9건:
- 짝수 해상도 → yuv420p, 홀수 3종 → bgr24 폴백
- I420 버퍼 = w·h·1.5B (바이트 수 어긋나면 ffmpeg 가 프레임을 밀어 읽는다)
- **실제 ffmpeg 왕복**으로 플레인 순서 검증 (무손실 ffv1 저장 후 디코드)
- 기존 bgr24 경로와 일치 (매끄러운 프레임 >40dB)
- 원본 충실도가 bgr24 이상
- **네거티브 컨트롤**: yuv420p 로 선언하고 bgr24 바이트를 보내면 프레임 수가
  안 맞는다 — 위 테스트들이 실제로 잡아낸다는 증거

`export_pano` 실경로 스모크도 통과(합성 4K 입력 → 15프레임, 폴백 없음,
디코드 정상). 전체 스위트 171건 통과.

**아직 안 한 것:** 프로덕션 해상도 실데이터 A/B(같은 정합·원본으로 두 포맷
비교). 시도했으나 9p 시크 + 분석 동시 실행으로 2분 내 완료 못 함 —
**기계가 한가할 때** 재시도. 따라서 실제 속도 개선폭은 아직 미측정이다.

## 다음 (측정 후 판단)

- ③ 프레임 병렬 렌더: `Renderer.render()` 는 읽기 전용 맵 + 지역 출력 버퍼라
  스레드 안전. 작은 풀로 여러 프레임 동시 렌더 + 순서 보장 → 유휴 4코어 활용,
  1.4~1.7배 기대. 반나절.
- ① 스티칭(CPU+NVENC)과 분석(GPU) 동시 실행 — 자원이 거의 겹치지 않아
  코드 수정 없이 처리량 ~2배. 재분석 배치에 바로 적용 가능.
- ② NVDEC 은 **보류**: 이 OpenCV(5.0.0)는 CUDA 없이 빌드돼 있어(`cuda`
  디바이스 0, `cudacodec` 없음, PyAV 미설치) 프로세스 내 NVDEC 경로가 없다.
  ffmpeg 서브프로세스 우회는 입력 파이프 866MB/s(2×4K BGR)를 새로 만들어
  아끼는 ~1코어보다 손해일 수 있고, `ChapteredVideo` 랜덤 시크(분석·OCR·GUI
  의존)를 잃는다. 제대로 하려면 CUDA 빌드 OpenCV 로 remap 까지 GPU.
