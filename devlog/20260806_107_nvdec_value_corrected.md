# 107 — 정정: CPU 디코드로도 3병렬이 된다 (NVDEC 이득은 9%)

2026-08-06. devlog 106 에 **"CPU 디코드로 3병렬은 디코드만 11.4코어라
8코어 머신에선 성립하지 않는다"** 고 적었다. **틀렸다.** 실측하니 잘 돌고,
NVDEC 이득은 병렬성을 여는 게 아니라 **9%** 다. "h264 를 hevc 로 재인코드
하면 어떠냐"는 질문에서 이 검증이 나왔다.

## 무엇이 틀렸나

디코드 **단독 벤치**(전속력 51.5fps, 3.81코어)를 3배로 외삽했다. 하지만
분석 중 디코드는 **분석 페이스(12.5fps)로만** 돌므로 실제 사용량은
3.81 × (12.5/51.5) ≈ 0.9코어다. devlog 101 에서 "개별 단계 벤치가 파이프라인
종단을 예측하지 못한다"고 적어놓고 같은 실수를 반복했다.

## 실측 — 3병렬, 디코드 백엔드만 다르게 (900프레임 × 3)

| | 합계 처리량 | 프로세스당 CPU | 총 CPU | SM |
|---|---|---|---|---|
| NVDEC | **35.91 fps** | ~1.0 코어 | ~3.0 | 69% |
| **CPU 디코드** | **32.91 fps** | ~1.8 코어 | **~5.4** | 58% |

개별: CPU 디코드 3병렬에서 10.72 / 11.22 / 10.97 fps (단독 13.31).

**8코어 중 5.4코어면 여유가 있다.** 3병렬은 NVDEC 없이도 된다.

## NVDEC 의 실제 가치 (수정)

| | devlog 106 의 주장 | 실제 |
|---|---|---|
| 3병렬 가능 여부 | NVDEC 필수 | **둘 다 가능** |
| 3병렬 처리량 이득 | — | **+9.1%** |
| CPU 절감 | — | 5.4 → 3.0 코어 |

9% 는 40시간 배치에서 ~3.5시간이다. 작지 않지만 **CUDA Toolkit + CUDA
OpenCV 환경 구성을 선행할 만한가**는 다시 판단해야 한다. CPU 2.4코어를
비워 배치 중에도 머신을 쓸 수 있다는 게 오히려 실질적 이점일 수 있다.

## 그래서 h264 → hevc 재인코딩은?

**분석 속도만 보면 손해다.**

| 1시간짜리 파노라마 1편 | |
|---|---|
| 재인코딩 비용 (30~80fps 가정) | **22~60분** |
| NVDEC 으로 아끼는 분석 시간 | **14분** |

재인코딩이 아끼는 것보다 오래 걸린다. 게다가 이미 손실 압축된 것을 다시
인코드하니 **세대 손실**이 얹힌다.

**저장 공간은 별개 논거다.** 구 h264 파노라마가 훨씬 헤프다:

| | 코덱 | 비트레이트 |
|---|---|---|
| pano_0374 (구) | h264 6348px | **109.8 Mbps** |
| pano_0002 (신) | hevc 5910px | **48.1 Mbps** |

2.3배 차이라 재인코드하면 용량이 절반 아래로 떨어진다. 다만 F: 에 2.8TB
여유가 있어 지금 급한 문제는 아니다 — **공간이 필요해질 때 하면 되고,
분석 속도를 근거로 지금 할 일은 아니다.**

## 교훈 (또)

- **개별 단계 벤치 × N ≠ 파이프라인 N병렬.** 단계는 파이프라인 페이스로
  스로틀되므로 전속력 측정을 외삽하면 과대평가한다. devlog 101 에서 같은
  실수를 하고도 반복했다 — 이번엔 "불가능"이라는 **결론까지 뒤집혔다.**
- 병렬 실험은 **바꾸려는 변수 하나만** 다르게 두고 재야 한다. 106 의
  4병렬 측정이 오염됐던 것도(1편이 CPU 폴백) 같은 종류다.
