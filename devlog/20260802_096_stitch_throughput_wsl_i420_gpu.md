# 096 — 스티칭 처리량 정리: WSL vs Windows, I420 A/B, GPU 경합

2026-08-02. "짧은 영상 다시 스티칭해서 얼마나 빨라지는지" 에서 출발해
devlog 088 의 17.44fps 미스터리까지 닫았다. **가장 큰 레버는 코드가 아니라
OS 였다.** 내가 앞서 말한 것 중 정정할 것도 여럿이다.

## 결론 먼저

같은 소재(20260801 짧은 세션 3분 구간), 같은 머신, **출력 5976×2270 고정**:

| 환경 | fps | 비고 |
|---|---|---|
| Windows + I420 (현행) | 10.3 | |
| Windows + bgr24 | 10.9 | I420 이전 동작 |
| **WSL + I420** | **17.1** | **Windows 대비 1.66배** |
| devlog 088 의 0392 | 17.44 | **WSL 이었다** |
| WSL + GPU 경로 | 23.72 | CPU 대비 1.39배 |

## 1. 088 의 17.44fps 는 WSL 값이었다

0392 프로젝트 파일의 소스 경로가 `/tmp/.../n9b_L/` — **리눅스 경로**다.
0392 는 WSL 에서 스티칭됐고, 오늘 측정은 전부 Windows 였다. 같은 소재를
WSL 에서 재니 **17.1fps** 로 17.44 와 사실상 일치한다.

즉 회귀도 이상 현상도 아니었다. **Windows 가 절반 속도인 것**이다.

배제된 후보들 (전부 실측):

| 후보 | 결과 |
|---|---|
| 내 벤치와의 경합 | 1.5% |
| I420 변경 | 5.8% (방향은 맞지만 크기 부족) |
| 출력 해상도 | 6022×2254 vs 5976×2270, 1% 내 |
| 소스 특성 | **59.94Mbps, 3840×2160, 29.97fps — 동일** |
| 렌즈 프로파일 | 동일 |
| **OS/런타임** | **1.66배** ← 이것 |

원인은 아직 모른다. 후보는 ffmpeg 빌드(WSL 6.1.1 vs Windows 8.0.1),
OpenCV 빌드, 파이프 I/O 처리, 스케줄링. **WSL 은 소스를 9p 로 읽고도
(더 느린 경로) 이겼다.**

실무적으로: `pano_0002`(3.63시간)를 WSL 에서 돌렸다면 **2.2시간**이었다.

## 2. I420 A/B — Windows 에선 회귀

`pipe_format()` 에 `PYSTITCH_PIPE_FMT` 오버라이드(devlog 095)를 넣고 같은
소재로 A/B. **두 실행의 출력 크기·el 범위가 완전히 동일**(5976×2270,
el +8.29/−48.94)하므로 비교가 성립한다.

| | fps | stitch 단계 | 출력 크기 |
|---|---|---|---|
| I420 (현행) | 10.3 | 652.0s | 1,083,729,745 |
| bgr24 (088 이전) | **10.9** | 621.9s | 1,083,742,685 |

**bgr24 가 5.8% 빠르다.** 출력 크기 차이는 0.001% 로 화질 트레이드오프도 없다.

088 의 논리는 "파이프 절반 + ffmpeg 색변환 제거로 ~0.9코어 회수"였는데,
그 변환은 **사라진 게 아니라 파이썬 writer 스레드로 옮겨갔다.**
`cv2.cvtColor` 는 단일 스레드고 swscale 은 SIMD+멀티스레드라 옮긴 쪽이
더 비쌌다. "writer 스레드는 놀고 있으니 공짜"라는 가정이 틀렸다.

단 WSL 에서는 17.1(I420) vs 17.44(0392, bgr24) 로 거의 차이가 없다 —
**파이프 최적화 효과가 OS 에 따라 달라진다.** 어느 쪽이든 OS 격차 66% 에
비하면 부차적이라, 되돌릴지는 WSL 이전 여부와 함께 판단할 일이다.

## 3. GPU 경로 — 처리량 1.39배, CPU 5배 절감, **그러나 SM 59%**

같은 출력(2270행) 기준, 4000프레임:

| | fps | CPU 코어 | SM | NVENC | NVDEC | VRAM |
|---|---|---|---|---|---|---|
| 스티칭 현행(CPU 경로) | 17.1 | ~4.1 | **9%** | 49% | 0% | 2.8GB |
| 스티칭 GPU 경로 | 23.72 | **0.77** | **59%** | 30% | 22% | 4.3GB |
| 분석 (TODOs 실측) | — | — | **52%** | 0% | 0% | — |

**여기서 트레이드오프가 분명해진다.** TODOs 의 "스티칭·분석 겹쳐 돌리기 —
자원이 거의 안 겹친다, 코드 수정 0" 은 현행 경로의 SM 9% 덕분이다.
9 + 52 = 61% 로 들어간다. GPU 경로로 바꾸면 **59 + 52 = 111%** 라 그 성질이
깨진다.

즉 GPU 스티칭은 **단독 실행이면 1.39배**지만, 겹쳐 돌리는 워크플로에서는
공짜 병렬성을 잃어 총량이 나빠질 수 있다.

## 4. 정정 — 내가 틀렸던 것들

- **"20260801 배치는 내 벤치와 경합해 측정에 못 쓴다"** → 과한 진단이었다.
  경합 없는 재실행이 10.34fps, 경합 중이던 원래 실행이 10.19fps 로 **1.5%**
  차이다. 내가 인용한 8.64fps 는 **분모에 정합과 프록시를 넣은** 값이었다.
- **"GPU 경로가 2.21배"** → 조건이 섞인 비교였다. GPU(WSL)를 CPU(Windows)와
  비교해 OS 효과가 들어갔다. 같은 OS·같은 출력이면 **1.39배**다.
- **프로토타입의 CPU 기준선(11.31fps)이 불공정했다.** `export_pano` 는
  **3단 스레드 파이프라인**(읽기→렌더→쓰기)인데 프로토타입 기준선은
  한 스레드 순차 루프다. 같은 WSL 에서 프로덕션 경로는 17.1fps 를 낸다.
  스크립트가 찍는 "처리량 2.0x" 는 이 불공정한 기준선 대비 값이다.

## 5. 제안

1. **다음 배치부터 WSL 에서 스티칭** — 코드 수정 0, 1.66배. 9p 는 병목이
   아님이 확인됐다(120MB/s vs 필요량 7.5MB/s)
2. **분석 입력 디코드에 NVDEC** — TODOs #2 가 "6022×2254 hevc 소프트
   디코드가 분석 CPU 의 큰 몫"이라고 짚은 그 지점. 오늘 만든
   `ChapteredGpuReader` 가 거의 그대로 쓰인다(파노라마는 단일 파일이라
   체인 로직도 불필요). **SM 을 안 건드리므로 분석과 경합하지 않는다.**
   100시간+ 배치에 직접 효과
3. **GPU 스티칭은 보류** — 1.39배를 얻자고 겹쳐 돌리기를 포기할지는
   워크플로 결정. 순차 실행이거나 CPU 를 비워야 할 때의 선택지
4. **I420 되돌리기는 WSL 이전과 묶어 판단** — Windows 를 계속 쓸 거면
   bgr24 가 5.8% 이득, WSL 로 가면 무의미
