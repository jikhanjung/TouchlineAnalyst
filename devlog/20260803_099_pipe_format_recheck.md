# 099 — 파이프 포맷 재측정: 096 의 결론이 뒤집혔다 (그리고 애초에 노이즈였다)

2026-08-03. devlog 098 로 render 가 빨라져 파이프가 병목에 근접했으므로,
096 의 I420 vs bgr24 A/B 를 같은 조건에서 다시 쟀다. **결론이 바뀌었고,
096 의 측정 방법 자체에도 문제가 있었다.**

## 결과 (3분 구간 5,394프레임, 5976×2270 고정, 출력 4건 모두 검증)

| 플랫폼 | yuv420p (I420) | bgr24 | |
|---|---|---|---|
| **WSL** | **22.7 fps** (288.6s) | 15.4 fps (400.8s) | I420 **+47%** |
| Windows | 15.7 fps (469.2s) | 15.1 fps (482.4s) | I420 +4% |

## WSL — I420 이 압도적으로 옳다

**+47%.** 098 에서 render 가 35.2ms(28fps)로 빨라지자 pipe(27.5ms, 36fps)가
바짝 붙었고, bgr24 는 파이프 바이트를 **2배**(1.5B/px → 3B/px)로 만든다.
파이프가 곧바로 병목이 되어 22.7 → 15.4fps 로 주저앉는다.

devlog 088 의 I420 변경은 **옳은 판단이었다.** 다만 그때는 render 가 지배적
병목이라 효과가 가려져 있었고, 096 에서는 심지어 회귀처럼 보였다.

## Windows — 4% 는 판정 불가다

여기서 방법론 문제가 드러난다. **같은 설정(Windows/yuv420p)을 두 번 쟀는데
7.7% 차이가 났다:**

| | stitch 단계 | fps |
|---|---|---|
| devlog 098 측정 | 508.2s | 14.2 |
| 이번 A/B | 469.2s | 15.7 |

**실행 간 편차가 7.7% 인데 A/B 차이가 4%** 다. 즉 Windows 쪽은 어느 쪽이
빠른지 **이 측정으로 말할 수 없다.**

그리고 이건 소급 적용된다 — **096 의 "Windows 에서 bgr24 가 5.8% 빠르다"도
같은 이유로 판정 불가였다.** 각 조건 1회씩 잰 5.8% 차이를 결론으로 적은 게
잘못이었다. 096 의 해당 항목은 무효로 본다.

## 정정

| | 096 의 기록 | 지금 |
|---|---|---|
| Windows I420 | **5.8% 회귀** | **판정 불가** (편차 7.7% > 차이 4%) |
| WSL I420 | "차이 거의 없음" | **+47%** (조건이 바뀜) |
| 088 의 I420 변경 | 회귀로 의심 | **옳았다** |

096 의 WSL 항목("17.1 vs 0392 의 17.44 로 거의 차이 없음")도 부정확했다 —
서로 다른 세션·다른 소재를 비교한 것이었고, 이번처럼 같은 소재로 A/B 하면
47% 가 나온다.

## 교훈 — 반복 없는 A/B 는 5% 대 차이를 못 가린다

이 머신의 실행 간 편차가 **7.7%** 다. 앞으로 이 급의 차이를 주장하려면
조건당 최소 3회 반복하고 편차를 함께 적어야 한다. 이번에 나온 결론 중
**WSL +47%** 만 노이즈를 확실히 넘고, 나머지는 전부 그 아래다.

지금까지 이 세션에서 5% 대 차이로 결론을 낸 것들 — 096 의 I420(5.8%),
097 의 맵 타입 종단(+7.3%) — 은 **재확인이 필요하다.** 097 의 렌더 단계
측정(+11%, 마이크로벤치 1.54배)은 반복성이 높은 in-process 측정이라
상대적으로 안전하다.

## 조치

기본값은 **그대로 I420 을 유지**한다. WSL 에서 명확히 옳고, Windows 에서는
판정 불가라 바꿀 근거가 없다. `PYSTITCH_PIPE_FMT` 토글은 남겨둔다.
